How RDF Canonicalization Is Used

How the Algorithm Works

The algorithm starts by separating triples into those that contain blank nodes and those that do not. Triples with no blank nodes get serialized straight into N-Quads format. The blank node triples are where the real work happens. For each blank node, the algorithm examines the surrounding graph structure and computes a hash-based label to replace the random identifier it was given. That label comes purely from the structure of the data, so the same structure always produces the same label regardless of where the data came from.

Once every blank node has a canonical label, those get substituted back into all the affected triples. Then the full dataset is serialized in N-Quads format, and each line is sorted alphabetically. The output is a sorted list of N-Quad strings that is always identical for equivalent datasets. That is what gets hashed and signed.

The example below shows how canonicalization treats blank node labels. Two datasets that describe the same thing but use different blank node identifiers will both produce the same output after running through the algorithm.

# Before canonicalization (same data, different blank node labels) Dataset A: _:b0 <knows> <Bob> . <Alice> <link> _:b0 . Dataset B: _:x1 <knows> <Bob> . <Alice> <link> _:x1 . # After RDF-Canon (both produce identical output) <Alice> <link> _:c14n0 . _:c14n0 <knows> <Bob> .

Verifiable Credentials

The most widely deployed use of RDF-Canon right now is in the W3C Verifiable Credentials ecosystem. A Verifiable Credential is a digital document, such as a diploma or license, that an issuer signs so anyone can verify it without going back to the issuer. The credentials are written in JSON-LD, which is an RDF format. Before signing, the issuer runs the credential through RDF-Canon to get a stable canonical form and signs that. When someone verifies the credential later, they run it through the same algorithm and check the signature against the output.

This is already in production. Universities and governments in multiple countries are issuing Verifiable Credentials, and all of them depend on RDF-Canon to validate their signatures. Without it, any formatting difference between the signed version and the version being verified would cause the check to fail.

The same approach extends to anything in the decentralized identity space. W3C DIDs and other linked data security standards all sit on top of this as a foundational piece. It is not a niche use case; it is core infrastructure for how digital trust on the web is being built out.

Developer Libraries

RDF-Canon is also available as a library for developers working directly with linked data. dotNetRDF is one example: an open-source library for working with RDF in C# and .NET. It includes a full implementation of the RDF Canonicalization API so developers can call the function on any RDF dataset and get the canonical N-Quads string back to work with however they need.

The W3C working group maintains an official test suite with hundreds of test cases that any conforming implementation has to pass. That is what guarantees all conforming libraries produce the same output, no matter what language or platform they are built on. A credential signed with JavaScript can be verified with Java, and the canonical forms will match.

Beyond credentials, the same tooling can be used to detect tampering in RDF datasets, deduplicate data across multiple sources, or generate stable checksums for versioning. Scientific data repositories use it so that a cited dataset version can be verified later. It covers a lot of ground beyond just signing.
